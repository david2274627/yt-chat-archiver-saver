### 2.2 ❗與實測資料矛盾：「直播收錄的訊息多半沒有頭像網址」
- T4 報告「限制與注意」寫：直播收錄的訊息多半沒有頭像網址，會看到首字圓點。
- 但 T3.6 實測 `fieldStats()`：text 2379 則中**有頭像 2376**、superchat 23／23、membership 6／7；`capture.js` 也只在 `src` 為 `https:` 時才存（`httpsOnly`）。所以資料庫中**大多數訊息都有 https 頭像網址**。
- 若實際在檢視器看到大量首字圓點，代表**顯示端有問題**（例如白名單比對、`referrerpolicy`、延遲載入、CSP）而不是資料缺漏。
- **要求**：(a) 更正報告說法；(b) 以 Service Worker 統計各場頭像網址的**網域分布**（只輸出網域與筆數，不輸出網址）寫入報告；(c) 依使用者實測結果（第 3 節第 4 步）判斷是否需修。

### 2.3 待使用者決定：Super Chat 字色
- 現行依對比度自動選黑或白：藍色 SC（`#1e88e5`）白字對比 3.8、黑字 5.5 → 用**黑字**，與 YouTube 原生白字不同。
- 選項：(a) 維持依對比度（可讀性優先，符合 SPEC 10.3 的 AA 要求）；(b) 與 YouTube 一致，一律白字或依 YouTube 的等級色表（可讀性在部分等級低於 AA）。
- 審查端建議 (a)，並在底色上加極淡的深色疊層讓白字也能達標的方案列為可選 (c)：底色以 `color-mix` 加深 15%，白字對比可達 4.5 以上，外觀接近 YouTube。

## 5. T4.1 修正
### 5.1 置頂重複
- 推定：同一則置頂在不同時間被擷取成**不同 id**（例如 YouTube 重新置頂、置頂列重新渲染時元素 id 改變，或降落／置頂以內容雜湊產生 id 時納入了時間）。
- **修正**：
  - 檢視器的置頂去重改以「作者＋正規化內容」為鍵，保留最新一筆；「較早的置頂」只列**內容不同**的。
  - 擷取端 `SAVE_PINNED` 同一場次同內容時，合併為同一筆，記錄 `pinnedAt` 首次與最後時間，不新增。
  - 既有重複由 `cleanupJunkSystem` 一併合併（或新增 `dedupePinned()`，預覽／執行兩段式）。
- 以 Service Worker 統計該場 `pinned_messages` 的筆數與 id 數，寫入報告，確認原因。

### 5.2 場次下拉選單訊息數不更新
- 收到 `NEW_MESSAGES` 時，更新目前場次在選單中的筆數；其他場次的筆數在**打開選單時**重新查詢（`LIST_STREAMS` 或直接唯讀查 `streams`），不需重新整理頁面。

### 5.3 ❗關閉再開啟擴充功能後沒有恢復收錄（B-1 實機未通過）
- 推定原因：重新注入的新實例與舊實例在**同一個隔離環境**，`content.js` 開頭呼叫舊實例的 `__ytcasRetire()`，而舊實例的 `connected()` 以**全域** `chrome.runtime.id` 判斷。若新注入讓同一環境的 `chrome` 物件可用，舊實例會誤判自己「仍連線」→ 回傳 `false` → **新實例放棄啟動**；舊實例隨後偵測到斷線而停止，結果**兩邊都不收錄**。（更新時能成功，可能是因為當時是不同的環境或時機不同。）
- **修正方向**：每個實例啟動時保存自己的連線憑證（例如 `const myRuntime = chrome.runtime` 與啟動時的 `myRuntime.id`，或與 background 交換的 instance token），`connected()` 以**自己的**憑證判斷；`__ytcasRetire()` 改為：只要新實例能與 background 通訊而舊實例的憑證已失效，就讓舊實例退場。另以 P6 `wake-check` 紀錄確認 SW 啟動檢查是否有對該分頁重新注入。
- 實機驗證：關閉再開啟擴充功能、以及 🔄 更新兩種情況都要恢復收錄（AC：5 秒內出現新實例的「擷取 observer 已掛上」，收錄統計持續增加）。建議使用者以 F-20 記錄驗證。

### 6.2 ❗流程問題：Claude Code 在使用者電腦上啟動其他瀏覽器並結束全部 Edge 程序
- 為了查證 5.3，Claude Code 以命令列啟動 **Edge 157 暫存設定檔**、用 DevTools 協定自動操作、連到 YouTube 公開直播，並且**曾以 `taskkill` 結束所有 `msedge.exe`**（報告已自行揭露並道歉）。
- 查證方式本身有價值，但「結束使用者所有 Edge 程序」可能造成使用者資料遺失，屬不應發生的操作。
- **`CLAUDE.md` 新增規則**（下一輪第一個 commit）：
  1. 不得結束、修改不是自己啟動的程序；結束程序一律以自己記錄的 PID 為準，不得以程式名稱批次結束。
  2. 啟動其他瀏覽器、自動化瀏覽器（DevTools 協定、Playwright 等）或對外部網站連線的測試，**先在報告或對話中徵得使用者同意**；同意後只用暫存設定檔、不登入、不碰使用者既有設定檔。
  3. 以上事件寫入報告的「事件」節。

### 6.3 記憶體用量（使用者提問：TVBS 24 小時直播分頁「高記憶體用量 1.7 GB」是否正常）
- 分頁記憶體包含：影片播放（MSE 緩衝、解碼、GPU）、YouTube 播放器與頁面程式、聊天室 iframe、**以及開著的 DevTools**（使用者的 Console 中有 7,659 筆以上的紀錄，DevTools 開啟時這些都保留在記憶體中）。單看一個數字無法判斷聊天室是否仍是主因。
- 程式面審查：擷取端的 `seenIds` 已有 2 萬筆上限；`#items` 節點維持 45；沒有發現無上限增長的結構。
- **需要量化驗證**（原始目標 F-01）：
  1. **F-20 新增探針 P9 記憶體**：每 5 分鐘記錄 top frame 與 chat frame 各自的 `performance.memory.usedJSHeapSize`／`totalJSHeapSize`（Chrome 專有 API，只有數字），以及 `#items` 節點數。`diag-report.js` 輸出隨時間的變化表。
  2. **對照測試**（寫入 `docs/test-checklist.md` 與 SPEC 第 9 節）：同一個高流量直播、相同畫質，**關閉 DevTools**，分別在「停用本套件」與「啟用本套件」兩種情況下開 60 分鐘；以 Chrome 工作管理員（Shift+Esc）記錄該分頁與「子框架：youtube.com（聊天室）」在 0／15／30／60 分鐘的記憶體，並以 P9 記錄 JS heap。判斷標準：啟用時聊天室子框架的記憶體不隨時間持續增長，停用時應可觀察到增長。
