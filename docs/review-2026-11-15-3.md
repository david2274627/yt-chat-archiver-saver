### 3.1 主題系統（取代 SPEC 10.2）
**設定**（`chrome.storage.sync`，所有介面共用，後台與 popup 皆可修改，變更即時套用到所有開啟中的介面）：

| 設定 | 選項 | 預設 |
|---|---|---|
| 主題模式 `themeMode` | `auto`（自動）／`light`（淺色）／`dark`（深色） | `auto` |

> 使用者 2026-11-15 確認：「手動調節深淺」指的是手動選擇淺色或深色兩種配色，**不需要**明暗程度滑桿。

**`auto` 的判斷來源**：
| 介面 | 來源 | 即時切換方式 |
|---|---|---|
| 內嵌面板、注入按鈕 | YouTube 目前實際套用的外觀（top frame `html[dark]`）。YouTube 外觀設為「使用裝置主題」時即等同系統設定 | top frame 以 `MutationObserver` 監看 `html` 的 `dark` 屬性 → `postMessage` 通知面板 iframe |
| 後台檢視器、popup、匯出 HTML | 系統設定 `prefers-color-scheme` | `matchMedia('(prefers-color-scheme: dark)').addEventListener('change', …)` |

> 內嵌面板跟隨 YouTube 而非直接跟隨系統，是為了避免「YouTube 是淺色、面板是深色」的突兀。若使用者把 YouTube 外觀設為「使用裝置主題」，兩者一致。

**UI 位置**：後台「設定」區與 popup 底部各一組分段按鈕「自動／淺色／深色」。內嵌面板不放設定 UI，但面板頂部列的 ⋯ 選單可提供「切換主題」快捷。

### 3.2 F-13（新）YouTube 禮物訊息
- **背景**：YouTube「禮物（Gifts）」是觀眾以 Jewels（在手機 App 購買的虛擬貨幣）送出的動畫貼圖，送出後會在聊天室顯示公告；近期已從直式直播擴展到橫式直播。這與「贈送會員資格（gift memberships）」是**不同的功能**。實機已確認輸入區有 `div#jewels-gifts-button`（筆記 2.5）。
- **新增類型 `gift`**（`constants.js` `MSG_TYPE.GIFT`）。欄位：作者、頭像、禮物名稱、禮物圖片、數量（若有）、Jewels 數值（若聊天室有顯示）、`timestampAbs`、`videoOffsetSec`。
- **分類**：
  | 類型 | 膠囊 |
  |---|---|
  | `superchat`、`supersticker`、`gift` | 💰 膠囊（文字改為「💰 SC／禮物」） |
  | 贈送會員（`gift-purchase`）、收到會員（`gift-redemption`）、新會員、里程碑 | 新增「👑 會員」膠囊 |
  > 膠囊列由 3 個變 4 個；D2 設計稿需確認 340px 寬時仍為單列（必要時「全部」只顯示數字）。
- **元件標籤未知**：聊天室中的禮物公告元件尚未在實機出現。擷取程式已有「未知元件 → `console.info` 一次並存為 `system`」的規則；請使用者在遇到禮物時跑診斷（第 5 節），取得標籤後再補 `selectors.js` 並把既存的 `system` 紀錄重新分類（提供一次性的重新分類函式）。
- 設計稿新增禮物訊息樣式（方向 B），與 SC 卡片可區分。

### 3.3 F-14（新）重複收錄與合併規則
**原則：一場直播／一部影片 = 一份存檔（以 `videoId` 為鍵）；同一則訊息只存一次（以 YouTube 訊息 id 為鍵）。重複進入只會「補進缺的」，不會覆蓋、也不會另存一份。**

| 情境 | 行為 |
|---|---|
| 同一場直播重新整理／離開再回來 | 同一份存檔；已存在的訊息以 id 略過，新訊息加入 |
| 直播結束後看 VOD 重播 | 同一份存檔（同 `videoId`）。重播訊息若與直播收錄的 id 相同 → 合併；不同 → 見下方後備去重 |
| 重複觀看同一部 VOD | 同一份存檔，不產生重複 |
| 兩個分頁同時開同一場 | background 以 `videoId` 為單位序列化寫入，`put` 為冪等，不重複 |
| 訊息被管理員刪除 | 保留原內容，標記 `deleted: true`、`deletedAt`；檢視器顯示「已刪除」標記（可篩選隱藏） |
| v2.6.0 舊資料遷移（F-11）、JSON 匯入 | 同一套合併規則 |

**欄位合併**（同一 id 再次出現時）：
- 不覆蓋已有的非空欄位（保留第一次收錄的內容）。
- 補齊空欄位：例如直播收錄時 `videoOffsetSec` 為推算值或 null，重播時可由 `#timestamp` 取得精確值 → 以重播值更新，並記錄 `offsetSource: 'replay'|'estimated'`。
- 更新 `lastSeenAt`；`sources` 累加（`live`、`replay`、`import`、`legacy`）。

**後備去重**（重播與直播的訊息 id 若不一致時才啟用）：
- 指紋 `fp = hash(type + authorHandle + 正規化後的訊息文字（含表符 alt） + round(videoOffsetSec / 3))`；同一 `videoId` 內 `fp` 相同視為同一則。
- **T3 必須先驗證**：同一場直播，直播中收錄的一則訊息與重播中同一則的 id 是否相同（只比對 id，不輸出內容），結果寫入 `docs/youtube-dom-notes.md`。若相同，後備去重只在 `fp` 命中且 id 不同時才合併，並記錄於診斷。

**收錄紀錄（新資料表 `capture_sessions`）**：每次開始收錄記一筆 `{ videoId, source: live|replay, startedAt, endedAt, firstOffset, lastOffset, added, merged }`。
- 用途：後台場次清單顯示「直播收錄 2 次・重播 1 次」，以及**時間軸覆蓋範圍**（因為只會收錄實際有開著的時段，中途離開的空檔一目了然）。
- 不需要「另存新檔」功能；若使用者想從頭重錄，提供「清空此場次後重新收錄」按鈕（需二次確認）。

**DB 版本**：新增 `capture_sessions` 與欄位 → `DB_VERSION` 升為 2，寫 `onupgradeneeded` 遷移（T2）。

## 7. 待議：劇院模式支援（使用者 2026-11-15 18:03 決定：**維持待議**，本版不排入任務）
劇院模式無法使用**與按鈕大小無關**。實機診斷顯示：劇院模式下 YouTube 把聊天室框固定成約 402×152（與視窗大小無關），而聊天室內容仍以約 320px 排版，原生輸入列本身就在可視範圍外。可能的方向：
- **A. 劇院模式時把聊天室框拉高**（只改 top frame 的 `#chat-container`／`ytd-live-chat-frame` 外框高度，不碰 iframe 內部佈局）。先前失敗都是「壓矮」；「拉高」理論上不會觸發 YouTube 的最小高度隱藏，但會改變劇院模式的頁面排版（聊天室往下延伸、頁面多一段捲動）。需 PoC 驗證。
- **B. Chrome 側邊欄（Side Panel）**：把優化面板放在瀏覽器內建側邊欄，與頁面版面完全無關，劇院模式、一般模式都能用；原生聊天室維持 YouTube 預設。需新增 `sidePanel` 權限（須使用者同意）。
- **C. 獨立小視窗**：以 popup 視窗開啟檢視器並與分頁同步。
審查端建議：A 成本最低，可在 T6 前做一個小 PoC；若 A 失敗或排版不可接受，再評估 B。**擷取與修剪在劇院模式本來就持續運作（AC 14），存檔不受影響。**

## 8. F-14 補充：待機室與直播結束後的聊天（使用者 18:03 提出，寫入 v27）
**背景**：直播開始前的待機室、以及直播結束後聊天室仍開放的幾分鐘，聊天室都在運作，但這兩段**不會出現在 VOD 重播裡**。這是套件存檔相對於 YouTube 重播的獨有價值，必須保留。

**規則**：
1. **照常收錄**：只要 `live_chat` 聊天室 iframe 存在、分頁開著，就擷取與修剪，不論直播是否已開始或已結束。
2. **新增欄位 `phase`**：`pre`（開播前）／`live`（直播中）／`post`（結束後）。
   - `pre`：`videoOffsetSec` 存**負值**（距開播的秒數）；若開播時間尚未確定，先存 `null`，開播後回填。
   - `post`：`videoOffsetSec` 依開播時間照算（會超過 VOD 長度）。
   - 判斷方式（待 T3 實機確認）：開播時間來源 `meta[itemprop="startDate"]` 在待機室是「預定時間」還是不存在、開播後如何變化；結束時的訊號（頁面是否出現「直播已結束」、`isLiveBroadcast`／`endDate` meta、聊天室系統訊息等）。以上只記錄標籤與屬性，寫入 `docs/youtube-dom-notes.md`。判斷不確定時 `phase` 依 `timestampAbs` 與已知開播／結束時間推算，並允許事後修正。
3. **檢視器呈現**：訊息清單以分隔線區隔「直播開始前（待機室）」「直播中」「直播結束後」；VOD 時間軸同步只作用於 `live` 段，`pre`／`post` 段不參與跟隨與跳轉（時間碼顯示為「開播前 12:34」「結束後 3:05」，不可點擊跳轉）。
4. **合併規則**：重播不會帶入 `pre`／`post` 訊息，這兩段只來自直播收錄；F-14 的合併與去重不受影響。`capture_sessions` 增加 `phases` 欄位，記錄該次收錄涵蓋哪幾段。
5. **AC**：在待機室開著聊天室 → 有存檔且標 `pre`；開播後同一份存檔繼續累加；結束後幾分鐘的訊息標 `post`；觀看 VOD 時 `pre`／`post` 訊息仍完整保留且不干擾時間軸同步。
6. 後台場次清單的覆蓋範圍顯示包含 `pre`／`post`。
7. **限制（寫入 1.3 非目標）**：沒有開著分頁的時段不會被收錄；YouTube 也不提供事後補抓待機室或結束後聊天的方式。

任務對應：4.1 規格 v27 一併寫入；T2（資料表欄位）、T3（擷取與 phase 判斷）、T4／T5（檢視器分段與時間軸排除）。
