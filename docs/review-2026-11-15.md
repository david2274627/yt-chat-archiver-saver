## 3. 問題分析

### 3.1 ❌ 量測 v2 把「全高容器」當成底部元素
`poc-chat.js` 的 `bottomZone()` 條件是 `rect.bottom > vh − 400 && rect.top < vh`，並排除 `#item-list` 及其祖先。但：
- 任何**不是 `#item-list` 祖先、卻佔滿整個高度**的元素（例如其他 `iron-pages` 分頁、覆蓋層容器、`#action-panel` 之類的空容器、高度 100% 的 `yt-live-chat-*` 包裝）都會符合條件，`top` 接近 0 → 露出值 ≈ iframe 高度。
- 真實頁面的結構與模擬頁不同，所以模擬頁沒抓到。

**使用者已於 03:32 以 Alt+Shift+D 貼回完整診斷**（Chrome 157、一般直播、預設雙欄版面、iframe 594px）。關鍵結構如下（**請整份存入 `docs/youtube-dom-notes.md`**）：

| 元素 | top / 高 | 父鏈 | 判讀 |
|---|---|---|---|
| `ytls-widget-overlay-manager` | 49 / 436 | `div#chat < div#contents < div#chat-messages` | **誤判元凶**。蓋在訊息列表上的透明覆蓋層容器（小工具／投票卡的掛載點），不是 `#item-list` 的祖先，所以沒被排除 |
| `yt-live-chat-banner-manager#live-chat-banner` | 485 / 52 | `div#contents < div#chat-messages < tp-yt-iron-pages#content-pages` | **置頂列**（輸入列上方）。內含 `yt-live-chat-banner-renderer > #banner-container > #header（yt-live-chat-banner-header-renderer，含 #menu-button）+ #contents（yt-live-chat-text-message-renderer#<訊息id>）`。**確認 `chat.bannerContainer` 選擇器仍正確** |
| `tp-yt-iron-pages#panel-pages` | 537 / 57 | `div#contents < div#chat-messages` | 內含 `div#input-panel`（538 / 56）→ `yt-live-chat-message-input-renderer#live-chat-message-input` → `#container > #top > #input-container > yt-live-chat-text-input-field-renderer#input` |

→ 正確的 `bottomZoneHeight` = 594 − 485 = **109px**（＋邊距 ≈ 使用者手動的 114px，吻合）。

其他確認：
- 頂部列子元素：`#primary-content, #title, #view-selector, #action-buttons, #viewer-leaderboard-entry-point, ytvl-live-viewer-leaderboard-chat-entry-point-view-model, yt-live-chat-button#live-chat-header-context-menu, yt-button-renderer, #close-button, yt-button-renderer`。**`⋮` 的實際 id 是 `#live-chat-header-context-menu`**，不是 `#overflow`（這次靠備援掛上，`headerHow: before-overflow` 的判定要修）。
- 錨點：`header: true`、`teaser: true（文字比對）`、`legacy: true`（舊列元素存在，但畫面上看不到，表示 `#show-hide-button` 可能以隱藏狀態殘留；掛載前須檢查可見性）。
- 版面：`frameParent = div#chat-container < div#secondary-inner`；`ytd-watch-flexy` 帶 `live-chat-present-and-expanded`、`panel-expanded`、`is-two-columns_`、`default-layout`、`flexy-small-window_` 等屬性，可用於判斷版面狀態（劇院模式的屬性待下一輪診斷）。
- `ytls-widget-overlay-manager` 已確認為 **YouTube 原生**（使用者 04:08 停用 Holodex+ 後仍為 true）。所有使用者都會有，量測與投票卡偵測必須處理它。

**修正要求**
1. `selectors.js` 填入 `chat.bottomZone`（**白名單**，依序）：`'yt-live-chat-banner-manager'`、`'#panel-pages'`、`'#input-panel'`；另加 `chat.bottomZoneOverlay = 'ytls-widget-overlay-manager'`（只取其**可見子元素**，例如投票卡，容器本身不計）；`chat.bottomZoneExclude`：`'#item-list'`、`'yt-live-chat-header-renderer'`、`'yt-live-chat-ticker-renderer'`、`'ytls-widget-overlay-manager'` 本身。
2. 量測 v3 = `iframe 高度 − min(白名單可見元素.top, 覆蓋層可見子元素.top)`；`#input-panel` 算法保留為後備。
3. **合理性檢查**仍要做：結果 > `iframe 高度 × 0.6`，或面板可見高度 < 160px → 判為可疑，退回後備算法並在狀態列標示。
4. 診斷清單維持輸出所有候選（含被排除者與原因）。
5. `chat.headerOverflow` 改為 `'#live-chat-header-context-menu', '#overflow', '#menu-button'`，並修正 `headerHow` 的回報。
6. 舊版列錨點：僅在 `#show-hide-button` **可見**（rect 寬高 > 0）時才掛載。
7. 投票卡的實際標籤仍未知（上次截圖有、這次直播沒有）：下一輪請使用者在有投票的直播再貼一次診斷，再把投票卡選擇器補進白名單。

### 3.2 ❌ 控制列不可達，使用者沒有逃生路徑
- 「展開 ▼」在截圖中不見，推測是狀態列文字過長換行，第二行被裁切蓋住。
- 一旦自動量測錯誤，使用者就無法切手動，也無法調整。

**修正要求**
1. 狀態列改為**單列、不換行**（`white-space:nowrap; overflow:hidden; text-overflow:ellipsis`），固定按鈕（展開、不裁切、關閉）放最前面或固定在右側且不被壓縮。
2. 新增**鍵盤調整**，不依賴畫面上的控制項：
   - `Alt+Shift+M`：自動／手動切換
   - `Alt+Shift+↑` / `Alt+Shift+↓`：手動露出值 ±8px（按住 Ctrl 為 ±32px）
   - `Alt+Shift+D`：複製診斷（已有）
   - 全部快速鍵列在 `docs/poc-clip-path.md`，狀態列收合時也顯示提示「Alt+Shift+M 手動」。
3. 面板頂部控制列的**可見高度保證**：面板至少保留 160px 可見（3.1 第 3 點），否則退回舊算法。

### 3.3 ⚠️ 尚未驗證的項目（因卡住）
- 頂部列「PoC 測試」按鈕是否出現、`⋮` 選擇器（`#overflow`）是否正確。
- 影片下方卡片按鈕。
- 投票卡、劇院模式、窄版面、付款視窗、Holodex+。
以上全部留到下一輪補測。

### 3.4 ⚠️ 模擬頁的侷限（流程改善）
- 連續兩輪「模擬頁通過、真實頁面失敗」，原因都是模擬頁的 YouTube 內部結構是猜的。
- **改善**：之後凡是依賴 YouTube DOM 結構的演算法（量測、錨點、彈窗偵測），模擬頁測試只能證明「程式沒寫錯」，**不能**寫成「✅ 通過」；報告中一律標為「模擬頁：邏輯檢查通過；真實結構待實機」。
- 使用者貼回的診斷資料（結構、標籤、id）應存進 `docs/youtube-dom-notes.md`，作為日後模擬頁與選擇器的唯一依據；每次有新資料就更新，標註日期與 Chrome 版本。
