## 3. 缺漏盤點

### 3.1 ❗ 背景分頁的計時器節流會讓 DOM 修剪失效（必修，影響核心目標 F-01）
- Chrome 對背景分頁有計時器節流，分頁在背景一段時間後，`setInterval` 可能被拖慢到約每分鐘才執行一次。F-01 目前寫的是「每 3.5 秒修剪」，在背景分頁（例如邊看別的分頁邊開著直播）時，聊天室 DOM 會持續累積，正是本套件要解決的記憶體問題。
- **修正**：修剪改為**以數量觸發為主、計時器為輔**：在擷取用的 `MutationObserver` 回呼中，節點數超過上限（45）就立即修剪已擷取的舊節點；`setInterval` 只作保底。寫入 F-01 與 AC：「分頁在背景 30 分鐘後，聊天室訊息節點數仍 ≤ 50」。
- 同理，擷取的批次送出（每 1 秒或 50 筆）也要以「筆數到了就送」為主，避免背景時資料積在記憶體。

### 3.2 ❗ Service Worker 會被 Chrome 隨時休眠（必修，影響資料完整）
- MV3 的 background 是 Service Worker，閒置一段時間會被終止，記憶體中的暫存佇列會消失。
- **修正**：background 收到 `SAVE_MESSAGES` 後**立即寫入 IndexedDB**，不在記憶體中累積；頻道名稱解析的待辦佇列存進 `chrome.storage.session`（或 IndexedDB），被喚醒後可接續；content script 端在 `sendMessage` 失敗（SW 重啟中）時重試 3 次，失敗的批次留在 content script 端下次一起送。寫入 3.2 與 T2 AC。

### 3.3 聊天室被關閉（✕）時無法收錄（需在 UI 告知）
- 擷取依賴聊天室 iframe；使用者按 `✕` 關掉聊天室後 iframe 被移除，收錄就停止（劇院模式不同：iframe 仍在，所以會繼續收錄）。
- **修正**：這是限制而非缺陷；寫入 1.3 非目標。popup 顯示目前分頁狀態：「收錄中」／「聊天室已關閉，未收錄」／「此影片沒有聊天室」。影片下方卡片的注入按鈕維持「開啟優化面板」（點擊會先展開聊天室）。

### 3.4 收錄範圍：哪些直播要自動存？（**需使用者決定**）
- 目前規格隱含「所有有聊天室的直播與 VOD 都自動收錄」，但沒有明文，也沒有開關。
- 選項：
  - (a) **全部自動收錄**（預設建議）＋ popup 有「暫停收錄此頻道」與「全域暫停」開關。
  - (b) 只收錄手動加入清單的頻道。
- 預設先實作 (a)；設定存在 `chrome.storage.sync`：`captureEnabled`（全域）、`captureExcludedChannels`（頻道 @handle 清單）。

### 3.5 儲存空間管理（**需使用者決定**）
- `unlimitedStorage` 不會被瀏覽器自動清除，但長期累積仍可能吃掉大量硬碟（高流量直播一場可達數萬則，加上頭像、表符網址）。規格目前沒有任何容量顯示或清理機制。
- 建議：
  - 後台顯示**總用量**（`navigator.storage.estimate()`）與**各場次的訊息數、估計大小**，場次清單可依大小排序。
  - 提供「批次刪除（勾選多個場次）」。
  - **不做**自動刪除（避免使用者不知情時資料消失）；改為用量超過 2 GB 時在後台顯示提醒（門檻可在設定調整）。
- 預設先照上述實作。

### 3.6 備份提醒（資料只存在一個地方）
- 本套件以「未封裝」方式載入，**在 `chrome://extensions` 按「移除」會連同所有存檔一起刪除**；Chrome 設定檔損毀、重灌也會失去資料。
- 建議（預設實作）：後台新增「**匯出全部（備份）**」：所有場次打包成單一 JSON 檔（沿用 v3 `formatVersion` 格式，可用 F-11 匯入還原）；後台頂部顯示「上次備份：N 天前」，超過 30 天顯示提醒。
- `docs/HANDOFF.md` 與 README 的安裝說明加註：**不要在 `chrome://extensions` 按「移除」**，更新程式碼請用 `git pull` 後按 🔄。

### 3.7 VOD 只會收錄「實際播放過」的部分（說明＋待議功能）
- 重播聊天室是隨播放進度逐步出現的；跳著看、只看一半，就只會存到看過的部分（覆蓋範圍條會顯示空檔）。
- 若要「一次下載整部 VOD 的聊天紀錄」，需呼叫 YouTube 內部的聊天續載介面，可行但較脆弱、容易因 YouTube 改版失效。**列為 3.0.0 之後的待議功能**，本版不做；寫入 1.3。

## 6. F-17 自動備份（取代 3.6 的「提醒」方案）

### 6.1 行為
| 項目 | 規格 |
|---|---|
| 頻率 | **每週一次**（`chrome.alarms`，週期 7 天；首次於安裝或啟用後 7 天）。Chrome 沒開著時錯過的排程，會在下次開啟 Chrome 後補做一次 |
| 內容 | 全部場次的完整備份（v3 匯出格式＋`formatVersion`），以 `CompressionStream('gzip')` 壓縮為 `.json.gz`；F-11 匯入需支援 `.json.gz` |
| 檔名 | `yt-chat-archive-backup-YYYYMMDD-HHmm.json.gz` |
| 失敗重試 | 失敗後自動重試，**最多 3 次**，間隔 10 分鐘 → 1 小時 → 6 小時（以 `chrome.alarms` 排程，SW 休眠不影響） |
| 失敗通知 | 3 次都失敗才通知「本次自動備份失敗」：系統通知（`chrome.notifications`）＋套件圖示紅色「!」標記＋後台頂部橫幅（含失敗原因與「立即重試」按鈕）。系統通知可在設定中關閉 |
| 成功 | 不通知；後台顯示「上次自動備份：日期、大小、位置」 |
| 手動 | 後台保留「立即備份」按鈕，行為與自動備份相同 |
| 舊備份保留 | 預設保留**最近 4 份**，可設定（1～52，或「全部保留」）。只刪除本套件自己產生、且確認存在於備份位置的備份檔。**聊天資料本身永不自動刪除**（第 4 節第 2 點） |
| 紀錄 | 每次備份（含重試）寫入 `chrome.storage.local` 的 `backupLog`（保留最近 20 筆：時間、結果、大小、位置、錯誤訊息） |

### 6.2 備份位置（可選）
Chrome 擴充功能在背景**不能任意寫入硬碟的任何路徑**，因此提供兩種位置模式：

| 模式 | 說明 | 可靠度 |
|---|---|---|
| **A. 下載資料夾內的子資料夾**（預設） | 例如 `下載\YT聊天室備份\`，子資料夾名稱可設定。使用 `chrome.downloads`（`saveAs: false`、`conflictAction: 'uniquify'`） | 高；不需每次授權。需新增 `downloads` 權限 |
| **B. 自選資料夾**（例如 `E:\Backup\`） | 使用者在後台按「選擇資料夾」（File System Access API `showDirectoryPicker()`），資料夾授權存於 IndexedDB；排程備份時由 offscreen document（`chrome.offscreen`）寫入 | **需先 PoC**：Chrome 對已授權資料夾的權限是否能在背景持續有效、offscreen document 能否寫入。若授權失效，該次備份視為失敗並依重試規則處理；3 次都失敗時，通知內容需說明「需要重新授權資料夾」並提供一鍵重新授權。**不會自動改存到模式 A**（避免使用者以為存在自選位置） |

- 新增權限：`alarms`、`downloads`、`notifications`、`offscreen`（使用者 2026-11-15 已要求此功能，視為同意；寫入第 7 節權限列與 CHANGELOG）。
- **T7 先做模式 A 與排程、重試、通知**；模式 B 另開 PoC 任務（T7-b），PoC 結果寫入 `docs/` 後再決定是否正式提供。

## 7. F-18（新）VOD 版本：原始收錄與重新剪輯分開

### 7.1 情境分析
| 情境 | 現行 F-14 下會發生什麼 | 問題 |
|---|---|---|
| 主播**刪除或隱藏原 VOD，另外上傳剪輯版** | 新上傳的是**不同 `videoId`**；一般上傳影片沒有聊天重播 | 原始存檔不受影響，**本來就分開**；但無法用剪輯版影片搭配原始聊天回看 |
| 主播**在 YouTube 工作室直接剪輯原 VOD**（同一個 `videoId`） | 若剪輯後仍有聊天重播，重播收錄時「重播的 offset 優先」會**覆蓋原始時間碼** | **原始時間軸被改寫**，與剪輯前不一致（剪掉的段落之後的訊息時間全部位移） |

> 剪輯後 YouTube 是否保留聊天重播、時間碼如何對應，尚未實機確認；本規格以「可能保留且時間碼會位移」為前提設計，T3 遇到時記錄於 `docs/youtube-dom-notes.md`。

### 7.2 規則
1. **原始收錄永不改寫**：直播中收錄的 `videoOffsetSec`（`offsetSource: 'live-estimated'` 或首次重播取得的值）視為**原始版本 v1**，之後任何重播都不得覆蓋（修正 F-14「重播 offset 優先」規則：僅在 v1 尚無精確值且影片長度與 v1 相符時才補值）。
2. **版本偵測**：重播收錄開始時讀取影片長度（`video.duration`，四捨五入到秒）。與該場次已知版本的長度差 > 2 秒 → 建立新版本 `v2`、`v3`…；`streams.versions[] = { id, duration, firstSeenAt, label }`（`label` 預設「原始」「剪輯版 1」…，可改名）。
3. **offset 分版本儲存**：訊息新增 `offsets: { v1: 秒, v2: 秒, … }`；`videoOffsetSec` 保留為 v1 的值（相容）。同一則訊息在新版本重播中出現，就寫入該版本的 offset；**在新版本中沒出現的訊息（被剪掉的段落）不刪除**，只是沒有該版本的 offset。
4. **檢視器**：場次有多個版本時，顯示版本切換（「原始 2:31:05」「剪輯版 1 2:10:44」）。觀看 VOD 時自動選擇與目前影片長度相符的版本進行時間軸同步；選「原始」時顯示全部訊息，選剪輯版時被剪掉段落的訊息以淡色顯示並標「剪輯版中不存在」。
5. **匯出**：HTML／JSON 匯出可選「原始版本」「指定剪輯版本」「全部（含所有版本 offset）」。JSON 一律保留所有版本資料（`formatVersion` 升級，匯入相容舊格式）。
6. **重新上傳成新影片（不同 `videoId`）**：後台場次提供「**連結剪輯版影片**」：輸入新影片網址，建立 `linkedVideos[] = { videoId, label, offsetShift }`。觀看該新影片時，檢視器可載入原始場次的聊天，以使用者設定的**時間差**（`offsetShift`，可在檢視器內用 ±1 秒／±10 秒按鈕微調）同步。中段剪接造成的多段位移列為之後的待議功能。
7. **AC**：(a) 同一 `videoId` 先直播收錄、再於影片長度改變後重播收錄 → 產生 v2，v1 的時間碼完全不變；(b) 兩個版本各自匯出，時間碼分別正確；(c) 連結新上傳影片並設定時間差後，Click-to-Seek 跳到正確位置。

## 8. F-19（新）彈出式聊天室視窗（使用者 19:50 提出）

### 8.1 背景與現況
- YouTube 聊天室選單「在彈出式視窗中開啟聊天室」會開一個獨立視窗，網址為 `https://www.youtube.com/live_chat?is_popout=1&v=<videoId>`。這個視窗**不跟著主分頁走**：主播降落（raid）到別的直播間、主分頁被導向新直播後，彈出視窗仍停在原直播的聊天室，直播結束後的聊天也會繼續顯示。
- **現行程式不支援**：`src/content.js` 以 `!isTop && path.startsWith('/live_chat')` 判斷聊天室，彈出視窗的聊天室是**頂層頁面**（`isTop === true`），會被當成一般頁面而不擷取。

### 8.2 規則
1. **辨識**：頂層頁面且路徑為 `/live_chat` 或 `/live_chat_replay`（不論是否有 `is_popout`）→ 視為「彈出式聊天室」，執行與嵌入式聊天室相同的擷取（F-02）、修剪（F-01）、F-12 自動切換「即時聊天室」。
2. **videoId**：取自網址參數 `v`；取不到時 `warnOnce` 並不收錄。
3. **場次資訊**：彈出視窗沒有標題、開播時間等資料 → background 以 `fetch('https://www.youtube.com/watch?v=<videoId>')` 取得 `meta[itemprop="startDate"]`、`endDate`（若有）、標題、頻道（只讀這幾個 meta，結果快取於 `streams`；已有資料則不重抓）。開播時間取不到時，`phase` 依 F-14 第 8 節的推算規則處理。
4. **與主分頁同時開啟**：主分頁的嵌入式聊天室與彈出視窗同時收錄同一 `videoId` → 依 F-14「兩個分頁同時開同一場」，以 id 去重，不重複。`capture_sessions` 的 `source` 新增 `popout`。
5. **降落情境**（使用者需求）：主分頁被導向新直播後，主分頁改收錄**新直播**（新 `videoId`，獨立存檔）；彈出視窗**繼續收錄原直播**的 `post` 段。兩份存檔互不干擾。降落橫幅（`yt-live-chat-banner-redirect-renderer`）若同時出現在兩邊，各自存入各自的場次。
   - 待實機確認：降落時彈出視窗是否也會被 YouTube 自動導向新直播的聊天室。若會，彈出視窗改收錄新直播；原直播的 `post` 段就只能靠「不跟隨導向」的那一邊。結果記錄於 `docs/youtube-dom-notes.md`。
6. **彈出視窗內的優化面板**（**待使用者決定**，見第 9 節）：
   - (a) 只收錄、不顯示面板【預設】：彈出視窗維持原生聊天室外觀，記憶體修剪與存檔照常。
   - (b) 也顯示優化面板：彈出視窗沒有 `ytd-live-chat-frame` 外框，F-10 的 clip-path 方式不適用；改為把面板覆蓋在原生訊息列表（`#item-list`）的範圍上、底部互動區不覆蓋（同樣以 `bottomZoneHeight` 量測）。需另做 PoC。
   - 無論哪種，彈出視窗沒有影片播放器，**VOD 時間軸同步不適用**。
7. **popup 狀態**：popup 只反映目前分頁；彈出視窗的收錄狀態顯示在後台場次清單（「收錄中：彈出視窗」）。
8. **AC**：(a) 只開彈出視窗觀看直播 → 有存檔、DOM 節點 ≤ 50；(b) 主分頁與彈出視窗同開 → 不重複；(c) 主播降落後，彈出視窗持續收錄原直播的結束後聊天（`phase: post`），主分頁收錄新直播，兩份存檔各自正確；(d) 彈出視窗中 F-12 有切到「即時聊天室」。

## 10. F-19 補充：彈出視窗中途開啟／關閉的收錄連續性（使用者 19:59 提出，**收錄優先**）

### 10.1 情境
直播進行中，使用者可能隨時「在彈出式視窗中開啟聊天室」，之後又關掉彈出視窗、回到主分頁的嵌入式聊天室，且可能反覆多次。

### 10.2 會不會影響收錄
- **不會重複、不會覆蓋**：兩邊都以同一個 `videoId` 存入同一份存檔，訊息以 id 去重（F-14）。
- **可能出現空檔**：切換的瞬間，若一邊已停止、另一邊尚未載入，期間的訊息可能漏掉；若主分頁在彈出後把嵌入式聊天室收起或移除、而使用者關掉彈出視窗後沒有重新展開，就會一直沒有收錄。

### 10.3 規則
1. **啟動時先掃描既有訊息**（適用所有收錄來源，不只彈出視窗）：聊天室載入時 YouTube 會一次帶出最近一批訊息，`MutationObserver` 只看得到之後新增的節點，所以開始收錄時必須先把 `#items` 內已存在的訊息全部擷取一次。這批「回溯訊息」能補上切換瞬間的大部分空檔，重複的部分由 id 去重。**此條為 F-02 的通則，T3 必做。**
2. **交接紀錄**：每個收錄來源（嵌入式、彈出視窗）各自建立 `capture_sessions`，`source` 分別為 `live`／`popout`（重播為 `replay`）。後台覆蓋範圍條把同一場的所有 session 合併顯示；**真正的空檔**（所有 session 都沒涵蓋的時段）以醒目樣式標出。
3. **關掉彈出視窗後自動接手**（預設開啟，可在設定關閉）：主分頁偵測到同一 `videoId` 的彈出視窗收錄結束（background 收到 `CAPTURE_END{source:'popout'}`），而主分頁的嵌入式聊天室處於收起或移除狀態 → 主分頁自動展開聊天室恢復收錄。展開後依 F-09 預設開啟優化面板（劇院模式則依 6.2 退讓，僅收錄）。
4. **彈出視窗開啟時主分頁的行為**：待 T3 實機確認——開啟彈出視窗後，主分頁的嵌入式聊天室是否仍存在、是否仍收到訊息（只記錄結構與屬性，寫入 `docs/youtube-dom-notes.md`）。
   - 若仍存在：兩邊同時收錄，去重即可，不需特別處理。
   - 若被移除或改成提示畫面：主分頁不收錄，由彈出視窗負責；適用第 3 點的自動接手。
5. **AC**：(a) 直播中開啟彈出視窗 → 關閉 → 再開啟 → 再關閉，重複 3 次，存檔中沒有重複訊息；(b) 每次切換後，回溯訊息補上切換期間的訊息（以切換前後各 1 分鐘的訊息數與 YouTube 重播比對，或以時間連續性檢查）；(c) 關掉彈出視窗後，主分頁 5 秒內自動恢復收錄；(d) 後台覆蓋範圍條正確顯示各來源與空檔。
