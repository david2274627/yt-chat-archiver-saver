# 審查報告（十）：擴充功能「錯誤」頁的警告堆積（T3.2 小修）

| 項目 | 內容 |
|---|---|
| 日期 | 2026-11-16 |
| 來源 | 使用者回報：`chrome://extensions` 卡片上的「錯誤」按鈕一直存在、清不掉（附截圖） |
| 結論 | 不是程式錯誤，是 `warnOnce()` 的 `console.warn` 被 Chrome 收進擴充功能的「錯誤」頁。需調整診斷輸出等級，避免使用者誤以為套件壞掉 |

> **給 Claude Code**：完成第 3 節（一個 commit），在 T3 報告末尾追加「T3.2」一小節，然後停下等使用者實測。

## 1. 使用者回報的內容
「錯誤」頁全部是**黃色警告**（不是紅色錯誤），內容重複出現以下 4 種：
- `[ytcas] 找不到 YouTube 元素：poc:anchor:header 聊天室頂部列 …（chat frame 未回報）`
- `[ytcas] 找不到 YouTube 元素：poc:anchor:legacy 舊版「隱藏聊天室」列 …（目前版面沒有屬正常）`
- `[ytcas] 找不到 YouTube 元素：poc:anchor:teaser 影片下方「聊天室」卡片 …`
- `[ytcas-poc] 找不到開關錨點 …→ 請用 Alt+Shift+P 開啟`

Service Worker Console：No errors。舊資料遷移結果正確（5 場、1,116 則、4 置頂、149 頻道，舊庫筆數不變）。

## 2. 原因
1. Chrome 會把 content script 的 `console.warn`／`console.error` 收進擴充功能「錯誤」頁，而且**跨頁面累積、不會自動清除**。
2. PoC 在**所有** YouTube 頁面執行（首頁、一般影片、沒有聊天室的影片），找不到聊天室錨點是正常狀況，卻以 `warn` 輸出。`warnOnce` 只在同一頁面內去重，每開一個頁面就再記一次。
3. `poc:anchor:legacy` 在目前版面**永遠**找不到，本身就註明「屬正常」，不應該是警告。

## 3. 修正（T3.2，一個 commit：`fix: 診斷輸出分級，避免擴充功能錯誤頁堆積`）
1. **分級規則**（寫入 SPEC 第 7 節「相容」列與 `CLAUDE.md`）：
   - `console.warn`：只用於**預期應該存在卻找不到**、且會影響功能的情況。條件：該頁確定有聊天室，例如 `ytd-watch-flexy[live-chat-present-and-expanded]` 或 chat frame 已回報，但錨點／選擇器仍找不到。
   - `console.info`：沒有聊天室的頁面、舊版相容錨點（legacy）、PoC 的一般提示。
   - `console.debug`：診斷細節。
2. `warnOnce` 新增第三個參數 `level`（預設 `info`），呼叫端依上述規則指定；PoC 的「找不到開關錨點」改為只在「有聊天室且所有錨點都失敗」時 `warn` 一次。
3. `poc:anchor:legacy` 改為 `debug`。
4. 頁面沒有聊天室時，PoC 不嘗試掛載錨點（不輸出任何東西）。
5. 驗證：在 YouTube 首頁、一般影片、有聊天室的直播各開一次，擴充功能「錯誤」頁不應新增任何項目（使用者實測時順便確認）。

## 4. 給使用者
- 「錯誤」頁的內容是**警告訊息，不是套件故障**；可按右上角「全部清除」。
- 修正後，只有真的出問題時才會出現在「錯誤」頁。

| 前一場直播（`EYoA…`） | `domNodes: 76`、`trimmed: 39`、`idMerged: 227`（在首次收錄中偏高） |

## B. 分析
1. **修剪規則的缺陷（確定）**：`trim()` 從最舊的節點往後掃，**只移除已標記的節點**，未標記的跳過。只要列表開頭有一批未標記的舊節點，新訊息一進來、被標記後，就會成為「第一個可移除的節點」而被**立刻移除**；舊的未標記節點則永遠留著。結果是：DOM 永遠卡在未標記節點的數量（76）、新訊息一出現就被刪掉、原生聊天室畫面看起來凍結。這與 `domNodes` 長期停在 76、可見清單 0 標記一致。
2. **為什麼會有一整批未標記的節點（待查）**：可能原因（請以實際程式與實機查證，不要只猜）：
   - 這批節點是在 `mode !== 'capturing'`（`pending`、等待 `STREAM_INFO`／`CAPTURE_START`）時加入的，`captureNode()` 直接 `return` 而不標記；之後的 `backfill()` 因為 `st.items` 不同或時機問題沒有涵蓋到。
   - F-12 切換「即時聊天室」後，YouTube 以新的一批節點重新渲染列表，而切換發生在 `backfill()` 之後。
   - `idMerged` 在首次收錄就偏高（227／290），表示同一批節點可能被擷取多次（例如重新掛上 observer 時重跑 `backfill()`），也需一併確認。
3. **10 秒觀察新增 0 的矛盾**：`captured` 每分鐘增加約 190 則，但可見 `#items` 在 10 秒內沒有任何新增節點。請確認 `st.items` 是否就是可見的 `#items`、或是否在其他元素（已脫離 DOM 的舊列表、另一個容器）上擷取；若是前者，確認 YouTube 新增節點的方式（是否先加入再被我們的 `trim()` 在同一微任務內移除、或 YouTube 改為更新既有節點內容）。

## C. 修正要求（T3.3）
1. **`trim()` 一律從最舊的節點移除**，不得移除比未標記節點更新的節點。最舊節點未標記時：
   - 若目前為 `capturing`：先對它呼叫 `captureNode()`（立即擷取並標記），再移除。
   - 若擷取失敗（`parseMessage` 回 null）：標 `skip` 後移除。
   - 非 `capturing` 模式：維持現行（`freeAll` 直接移除）；`pending` 等待中則保留，但設**硬上限**（例如 200）：超過時先擷取再移除最舊的，避免無限累積。
2. **`attach()` 或 `beginCapture()` 之後、以及 F-12 切換完成之後**都執行一次 `backfill()`；`backfill()` 前先確認 `st.items === doc.querySelector(S.chat.items)`。
3. **收錄統計新增診斷欄位**：`itemsIsCurrent`（`st.items` 是否等於目前可見的 `#items` 且 `isConnected`）、`unmarkedNodes`（`#items` 中未標記的數量）、`observedAdded`（observer 這一分鐘看到的新增節點數）、`backfillRuns`。
4. **AC 補充**（F-01）：連續收錄 5 分鐘後，`#items` 子節點 ≤ 50、其中未標記數 ≤ 5；新訊息在原生聊天室中可見至少到被更新的訊息推出上限為止（即不可「一出現就被移除」）。
5. 模擬頁測試補兩個情境：(a) 開始收錄前列表已有 76 個未標記節點、`pending` 期間又加入 20 個；(b) F-12 切換後列表整批重建。兩者都要在收錄開始後 ≤ 50 且全數擷取。
6. 完成後在 T3 報告末尾追加「T3.3」，並列出 B-2、B-3 的原因結論。

## D. 實測順序調整

## B. 分析
### B-1 ❗子元素被當成訊息擷取（確定，程式碼已確認）
- `attach()` 為了偵測刪除狀態，observer 選項是 `{ childList: true, attributes: true, subtree: true, attributeFilter: ['is-deleted'] }`。**`subtree: true` 會讓 `childList` 也回報所有後代節點的新增**（訊息內部的徽章、圖示、按鈕、文字 span 等）。
- `onItemsMutation()` 對所有 `addedNodes` 呼叫 `captureNode()`，沒有檢查是否為 `#items` 的直接子節點 → 這些子元素被 `parseMessage()` 當成「未知元件」解析，**以 `type: 'system'` 寫入資料庫**（垃圾紀錄），並灌高 `captured`／`observedAdded`。
- 這也解釋了 `observedAdded` 偏高。`dupCaptured`（約 95）是否也受影響，修正後再看。

### B-2 `dupCaptured` 約佔 35%（待修正後再判斷）
- 可能是一次性的：F-12 切換時 YouTube 以同 id 整批重建列表（`backfillRuns: 2`、`backfillCaptured: 150`）。
- 也可能是持續的：YouTube 把被移除的節點重新插入。
- 判斷方法：修正 B-1 後，間隔 1 分鐘取兩次收錄統計；`dupCaptured` 不再增加 → 一次性，可接受；持續增加 → 進 T3.5（改為捲出可視範圍才移除等）。

### B-3 `yt-action` handler 超過 150ms
- 可能是 YouTube 自身，也可能是我們在 observer 中處理了大量子元素造成。B-1 修正後再觀察是否消失。

## C. T3.4 修正（每項一個 commit）
1. **只處理 `#items` 的直接子節點**：`onItemsMutation()` 中 `childList` 紀錄只取 `r.target === st.items` 的 `addedNodes`（其餘略過，不計入 `observedAdded`）。刪除偵測維持 `subtree` 屬性監看。`captureNode()` 開頭加防呆：`el.parentElement !== st.items` 時直接返回。「未知訊息元件」的 `console.info` 也只對直接子節點輸出。
2. **清除已寫入的垃圾紀錄**（資料庫維護，`fix(db): …`）：
   - 新增 `YTCAS_BG.cleanupJunkSystem({ dryRun })`：找出 `type: 'system'` 且 `rawTag` 屬於「非訊息元件」的紀錄。判定規則：`rawTag` **不是** `#items` 直接子節點的已知或可能標籤——即不以 `yt-live-chat-` 或 `ytd-sponsorships-` 開頭，**或**屬於明確的子元件清單（`yt-live-chat-author-badge-renderer`、`yt-live-chat-author-chip`、`yt-live-chat-text-input-field-renderer` 等，清單放 `selectors.js`）。
   - `dryRun: true` 只回傳各 `rawTag` 的筆數，不刪除；`dryRun: false` 才刪除並更新場次的 `messageCount`。
   - **只刪本版（T3 起）產生的垃圾紀錄**：限定 `sources` 只含 `live`／`popout`／`replay` 且 `firstSeenAt` ≥ T3 部署時間（2026-11-15 23:00 +08:00）；舊資料遷移與匯入的紀錄一律不動。
   - 報告中附 `dryRun` 結果（只有筆數）。
3. 模擬頁測試補：訊息節點內部後代被新增（徽章、圖示延遲渲染）時，不產生任何新紀錄、`observedAdded` 不增加。
4. 完成後在 T3 報告末尾追加「T3.4」，列出 B-2、B-3 的觀察方法，然後停下。
