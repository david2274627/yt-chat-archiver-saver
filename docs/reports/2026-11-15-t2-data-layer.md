## 4. 問題、事件與偏離規格之處

### 4.1 我自己補的設計細節（已寫入 SPEC v28，請確認）
1. **指紋去重只在不同來源之間比對**：否則同一位觀眾 3 秒內連發兩次「草」，兩則（id 不同）會被合併成一則。`live` 與 `popout` 視為同一來源。
2. **別名 `aliasIds`**：指紋合併時，記下新來的 id。否則同一則重播訊息下次再出現時，會因為第 1 點的限制被重複寫入。
3. **v2.6.0 舊 id 的別名**：舊 id 的格式是 `${videoId}_${YouTube 訊息 id}`。去掉前綴的部分存成別名，之後直播或重播收錄到同一則訊息時能直接合併；元素沒有 id 時用的亂數 id 不作別名。
4. **指紋只在 v1 時間軸計算**：重播屬於剪輯版（v2 之後）時不做指紋去重，因為兩個時間軸的秒數不同。
5. **沒有作者也沒有文字的訊息不算指紋**：例如沒有作者資訊的貼圖，避免不同人的訊息被合併。
6. 合併時的幾個例外：
   - 原本存為 `system`、這次收到已知類型時，改用新類型。
   - 刪除標記是新資訊，一律採用。
   - 只有 `lastSeenAt` 變動時仍會寫入，但不計入「合併」筆數，也不推播。
7. **清空後重新收錄**：版本清單（由收錄產生）一併清空，「連結剪輯版影片」（你自己輸入的）保留。
8. **事後重算 `phase`**：
   - 只處理有直播收錄來源（`live`、`legacy`、`import`）且 offset 不是重播精確值的紀錄。
   - offset 只在原本是空值、或是直播收錄的待機室訊息時才重算，其他已存在的 offset 不動，避免改到舊資料原有的時間碼。
9. **其他小規則**：
   - `sources` 記 `live`，不另外記 `popout`（`popout` 只記在收錄紀錄上）。
   - 頻道名稱解析失敗 6 次後，1 天內不再重試。
   - 匯入收錄紀錄時，以「來源＋開始時間」判斷是否重複。

### 4.2 事件
- **第一輪測試對 `www.youtube.com` 送出了 3 個請求**（`/@user1`～`/@user3`，都是測試用的假 handle）。
  - 原因：前面的測試存入訊息後，背景程式自動排入頻道名稱解析，而第一版測試頁沒有攔截 `fetch`。
  - 這 3 個請求都被瀏覽器的跨來源規則擋下，沒有帶 Cookie，也沒有任何你的資料。
  - 處理：測試頁改為一律攔截 `fetch`。修正後的那一輪，網路紀錄中沒有任何 YouTube 請求。

### 4.3 偏離與限制
- **測試方式**：審查建議 Node＋`fake-indexeddb`，但 CLAUDE.md 不允許 npm 相依，所以改用瀏覽器測試頁（審查列出的另一個做法），已寫入 SPEC 3.1。
- **刪除通知的時間差（留給 T3）**：`MESSAGE_DELETED` 送到時，如果那則訊息還沒寫入資料庫，會回 `found: false`。T3 的 content script 必須先送出那則訊息所在的批次，再送刪除通知。
- **`offsetSource` 的空值**：offset 本身為 null 時，`offsetSource` 也存 null（規格只列出 `replay`／`estimated`）。
- **權限與 manifest**：本輪沒有加入 F-17 需要的新權限，依規格留到 T7。
