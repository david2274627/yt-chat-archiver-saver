## 做法

### chat frame（聊天室 iframe 內，`src/chat-input.js`）
- **底部互動區高度**：沿用 T1 PoC 的白名單算法，也就是 iframe 底邊減去下列元素中最高的頂端。
  - 白名單：投票卡 `#chat > #action-panel`、置頂列、`#panel-pages`、`#input-panel`。
  - 覆蓋層 `ytls-widget-overlay-manager` 的可見子元素也算，但量出來超過 iframe 高度 60% 時不採計（避開 T1 那次 545px 的錯誤值）。
  - 都量不到時，用 `#input-panel` 頂端。
  - VOD 的 `#input-panel` 高度是 0，視為沒有輸入區。
- **彈窗**：表符選單、購買流程、下拉選單、對話框，取最上方的頂端。
  - `$` 選單長在 `#input-panel` 內，展開時輸入區本身變高，已經算在高度裡，所以不另外當成彈窗。
  - 頂部列內的下拉選單不算：F-12 自動切換時會短暫展開，而且頂部列本來就被裁掉。
- **何時回報**：輸入區或置頂列大小改變、點擊或按鍵之後、每 500ms 保底檢查。**狀態有變才送**，只有數字與布林。
- **面板開著時**：以 `visibility: hidden` 隱藏原生訊息列表與頂部列（SPEC 6.2 第 2 點）。
  - 不改任何 `height`／`display`，避開 6.1 列出的失敗路線。
  - 退讓或關閉面板時立即還原。

### top frame（`src/panel.js`）

### test-diag-page 的已知不穩定
- **根因**：「記錄 10 分鐘」時，診斷頁先用自己的時間算出停止時間，background 收到後才取開始時間（晚幾毫秒），所以實際只記 599,999 ms。
- 這不只是測試的問題，實際記錄也會少幾毫秒。
- **修正**：改成同時送時長，background 以實際開始時間加上時長計算停止時間。
- **測試**：加了一個確定性的測試，故意讓停止時間早 3 毫秒來重現。連跑 3 次都是 11／11。

### 1. 自己送出的訊息重複（30.5，資料正確性）
- **原因（推測）**：YouTube 先插入「送出中」的暫時節點，確認後換成正式節點，兩個 id 不同。
  - 第二份是「≈」，代表正式節點不是以「即時到達」擷取（回溯、補掃，或列表被換掉），時間退回顯示的分鐘。
  - 依 id 合併失敗；指紋的 3 秒分桶也對不上。
- **擷取端**：只看一般文字訊息，以「同作者＋同內容」配對最近 90 秒內擷取過的訊息。符合下列任一，就當成暫時節點：
  - id 是暫時格式。推測以 `LCC.` 開頭，**未驗證**。
  - 被頁面移除，而且不是本套件修剪、也不是列表開頭。
  - 所在的列表被整個換掉，而且沒有以同 id 重新出現。
- 配對到後：正式節點沿用暫時節點的時間（到達時間、offset、phase），並帶 `replacesId`。
  - 暫時節點比正式節點晚移除時，移除當下補送（事後配對）。
  - 同一個節點 id 原地改變時，一律合併。
- **background**：
  - 有 `replacesId` → 同作者同內容就合併。
  - 沒有提示 → **其中一筆是暫時 id**、≤ 90 秒才合併。
  - 以正式 id 為主，暫時 id 記入別名，場次筆數扣回。
  - 面板收到合併後的紀錄時，移除另一筆並依時間重排。
- **不會合併**：
  - 兩筆都是正式 id：同一個人連續送出相同內容、不同人的「8888」。
  - 不同作者、超過 90 秒。
  - 本套件修剪掉的、列表開頭被 YouTube 移除的。

### 2. 點 `$` 後底部互動區消失（30.3）

## 做法

### 0. `fixOwnDuplicates` 預覽 155 對（33.6）與 `s6wW…` 那一則（33.8.3）
- **暫時節點的條件**：符合 id 形狀還不夠，另外要：
  - 來源是直播（`live`／`popout`）。
  - 類型是一般文字。
  - `tsSource: 'arrival'`。
  - 和正式節點的時間差 ≤ 30 秒（v51 是 90 秒）。

  `db.js` 的 `isTempRec`（寫入時與 `fixOwnDuplicates`）和擷取端的 `isTempEntry` 用同一套規則。
- **v51 誤判的原因**：重播、遷移、匯入的資料，以及 SC／會員訊息，也有「`C` 開頭、≤ 31 字」的 id。這些都會被當成暫時 id，所以 `tempIds 803` 遠多於你實際送出的數量。
- **新測試**：重播來源、遷移資料、SC、會員的短 `C` 開頭 id 都不算暫時 id；超過 30 秒不配對。
- **預覽新增的分組**：
  - `tempShapes`：前 4 碼｜長度＋來源＋類型＋時間來源，符合規則的標 ✓。
  - `pairShapes`：每一對的形狀、來源、類型。
  - `pairDt`：時間差分布（≤ 10 秒／≤ 30 秒）。

  `tempShapeMatches` 是「只看形狀」的筆數，可以和 `tempIds` 對照。
- **`s6wW…`（`tempSeen 1`、合併全為 0）的經過**：
  1. 實機 P1 的 `idFromEmpty` 和即時到達筆數一樣多，表示 YouTube 幾乎每則都是「id 先清空、再設成正式 id」。
  2. 那一則也是「暫時 id → 空 → 正式 id」。v51 用空 id 找舊紀錄，找不到，所以沒合併。
  3. 結果暫時節點那筆已經存了，正式 id 又存成新的一筆，**重複了**。

  v52 改成用節點找最近一次的紀錄。清空後設回同一個 id 時，視為同一則，不會重送。
- **P1 `own` 的新欄位**：
  - `tempStored`：暫時節點已存、等正式節點合併。
  - `tempPending`：目前還在等。
  - `tempDropped`：從最近清單移除時（90 秒）還沒等到，兩筆都留著。
- **`unkn|55` 的來源還沒查到**。它不符合 v52 的暫時節點條件，除非它真的是直播文字、到達時間。這次預覽的 `pairShapes` 會列出來源與類型，你重跑後就看得出來。

### 1. 降落的資料正確性（33.1 第 1～5 點）
- **`streamCompare(a, b)`**：只輸出數字、代碼、4 碼 videoId，內容如下：
  - 兩場的筆數，以及 phase／`tsSource`／類型的分布。
  - 開播與結束時間和來源。
  - 各次收錄的紀錄。
  - 收錄開始前就有的筆數。
  - 標題、頻道是否相同（布林）。
  - 作者數與共同作者數。
  - b 裡「同作者同內容也在 a 出現」的筆數。
  - `crossVideo`。
  - a 降落後，b 收到「作者只在 a 出現」的筆數。
- **跨場次合併**：訊息 id 是全域唯一的。漏進新場次的訊息，之後原場次的彈出視窗再收到時，會合併到新場次那一筆，所以原場次只拿到少數幾則。v52 起把這種情況記在 `streams.crossVideo`（只存次數）。
- **嵌入式聊天室的 videoId 綁定後不換**：
  - 同一個聊天室文件收到不同 videoId 的 `STREAM_INFO` 時，會先送出剩下的訊息、結束收錄紀錄，再暫停（`video-mismatch`）。
  - 只有 `#items` 被換成「本頁沒看過任何 id」的新列表時，才重新綁定。
  - 記錄：P7 `video-switch`、P1 `videoMismatch`。

  dom-notes 2.10 記了降落時 iframe 與 `#items` 的變化（部分已驗證）。實際的 `#items` 換法要靠你錄 P7 確認。
- **導航後的標題與頻道**：
  - top frame 比對 microdata 自己的 videoId（`identifier` meta 或 `canonical`）和網址。
  - 不一致時只送 videoId 與播放器長度，每秒重試，最多 10 秒（P4 `meta-stale`／`meta-fresh`）。
  - 嵌入式聊天室沒有標題時，background 會抓 watch 頁補上。

  **這段 top frame 的檢查沒有測試頁**（runTop 沒有模擬頁），只做了程式審閱，請你實機確認。
- **降落＝原直播結束**：
  - 收錄中出現降落橫幅時，以降落時間暫定 `endedAt`（`endedAtSource: 'raid'`），之後的訊息標 `post`。
  - background 每 60 秒重新抓取（`raid-end`），等 meta 的 `endDate` 覆蓋。
  - 彈出視窗收錄時也一樣。
- **`fixRaidLeak('新','原')`**：
  - 候選訊息：新場次裡時間在原場次第一個降落橫幅前 1 分鐘之後、作者在原場次出現過、而且在新場次的其他時段都沒出現。另外加上和原場次降落橫幅同內容的那則。
  - 預覽只列筆數、phase 分布與時間跨度。
  - **規則要等你的 `streamCompare` 結果確認後才執行**。數字不合理的話，我會先調整規則。
- **`fixStreamMeta()`**：
  - 不帶參數時，列出同標題的場次組。
  - 帶 videoId 時預覽標題／頻道是否會改變，`{ dryRun: false }` 才寫入。
  - 會重新抓 watch 頁，也就是擴充功能平常的 `credentials: 'omit'` 請求。
