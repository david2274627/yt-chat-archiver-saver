## 摘要
- **面板與開關**：
  - 有聊天室的影片頁會**預設開啟**優化面板，面板放在 YouTube 聊天室元素裡面。
  - 面板頂部列有紅色「關閉優化面板」。面板關閉時，從聊天室頂部列 `⋮` 左邊的圖示按鈕，或影片下方「聊天室」卡片旁的按鈕開啟。

## 開發中發現並修正的問題
- **虛擬清單停止重繪**：瀏覽器窗格被遮住時 `requestAnimationFrame` 不觸發，清單停止重繪。現在 100ms 內未繪製就以 `setTimeout` 補上；iframe 在畫面外時也有幫助。
- **平滑捲動被誤判為使用者捲動**：平滑捲動途中的捲動事件會被當成使用者捲動，同步因此暫停。現在改為到達目標、使用者操作（滾輪、觸控、按鍵）或 2 秒逾時前都不判定為使用者捲動。

### (A) 時間軸同步整個失效（P0）
- **原因**：
  - 面板 iframe 的 `src` 用的是 `use_dynamic_url` 的動態 ID 網址，但面板文件的實際 origin 是擴充功能本身的 ID。
  - 證據有兩個：面板讀得到擴充功能的 IndexedDB（origin 不同的話資料庫會是空的）；`SEEK_TO` 是靠「擴充功能 ID」那個條件通過檢查的。
  - top 送訊息給面板時，以 `src` 的 origin 當目標，origin 不符，瀏覽器默默丟棄。所以 `VOD_TIME`、`THEME`、`CAPTURE_STATUS` 全部沒送到。
  - 面板因此一直停在「跟隨到底」模式：沒有藍框、拖曳不跟，「回到播放位置」也只會跳到清單最後。
  - 點時間碼跳轉是面板 → top 的方向，不受影響，所以正常。
- **修正**（`6d1beee`）：兩個 origin 各送一次；不符的那個會被丟棄，面板只會收到一次。
- **端對端測試** `test-e2e-panel.html`（新增）：
  - 測的是 top 端的真實 `panel.js` 和面板 iframe 內的真實 `viewer.js`。

  - `offsetSource`
  - `disorder`：依到達時間排序時 offset 倒退的筆數，按來源分

**原因（程式面）**：

- 只有 live 來源的訊息，offset 是「到達時間 − 開播」（含聊天延遲）；只有 replay 的訊息，offset 是影片時間。
- 清單依到達時間排序，三種混在一起就亂序。`syncPoints` 只保留遞增的部分，被點的那則不在同步點內，所以藍框落在前一個同步點（32:07）。

**修正**：
1. **以 replay 為準**：已合併的訊息用 replay offset。只有 live 來源的訊息，以 `(到達時間 − 開播) + 校正值` 參與同步與時間碼。
   - 校正值＝同場已合併訊息「replay offset − (到達時間 − 開播)」的中位數，至少 5 筆。
   - 沒有已合併的訊息時，以「同作者、同內容、各只出現一次」的 live／replay 配對計算。
2. VOD 模式（v1）的清單**依同步時間排序**，同步點因此涵蓋所有訊息。
3. 點時間碼後，藍框標在被點的那則，直到播放位置越過下一則，或往回超過 5 秒（跳轉的落點可能略早於目標，所以留這個餘裕）。
4. 連線狀態顯示「VOD 校正 ±N 秒（已合併 a、疑似重複 b、只有 live c）」。

### (L) 直播倒轉時藍框比畫面早約 1 分鐘
**能否取得直播延遲**：取不到。
- 播放器的直播延遲在「詳細統計資料」裡，只有使用者打開那個面板時才有 DOM。
- 播放器 API 是頁面的 JS，content script 的隔離環境讀不到，與 `timestampUsec` 同樣的限制。
- 技術上可以用 `chrome.scripting` 注入到頁面 world 呼叫播放器 API，但這是把程式放進 YouTube 頁面本身執行，超出目前的安全原則，**我沒有做**。若要考慮，需要你決定。

**修正**：
1. **錨點**：倒轉時的目標時間，改為「跳轉當下的位置 + 之後的播放進度」，不再每次都用 `seekEnd` 重算。
   - `seekEnd − currentTime` 在三場直播都約 3,556 秒，表示 `seekEnd` 不是真正的直播邊緣。它在倒轉期間怎麼前進無法保證；如果停住不動，v43 的目標會以 2 倍速往前跑，看了越久差越多。
   - 連線狀態新增「seekEnd 速度」（正常約 1.00），實機可以看出是否有這個問題。
2. **同步微調**：直播倒轉時，面板第二列顯示「同步微調：畫面落後 N 秒」與 −10／−1／+1／+10。
   - 依頻道記住；沒校正過的頻道沿用最近一次校正的值。
   - 預設 0。審查端建議預設用實測的典型延遲，但目前唯一的實測（約 1～2 分鐘）可能有一部分來自第 1 點的錨點問題，直接預設 60 秒有重複校正的風險。所以改成「你校正一次後，就成為之後的預設」。若你希望固定一個預設值，告訴我秒數即可。
3. **進入頁面時已不在最新**（徽章「非最新」、本頁還沒量到基準）：沿用上次記住的基準，連線狀態標示「基準 N，沿用上次」。你點「直播」回到最新後，改用本頁量到的值。從沒量過時沒有基準，目標會偏早，請回到最新一次再倒轉。

**你可以操作的校正方法**（【可倒轉直播】）：
1. 往回拖 1～3 分鐘。
2. 方法 A（畫面上有時鐘時）：
   1. 打開 ⋯「連線狀態」，看「目標 hh:mm:ss」。
   2. 和畫面上主播的時鐘比較，算出「目標 − 畫面時鐘」差幾秒，按 + 那麼多秒。

### 20.2 直播倒轉：牆上時間錨點
**探針先行**：
- P10 先單獨 commit。
- 假設「在最新期間 `A = now − currentTime×1000` 穩定」只能在實機確認，所以錨點的程式也在本輪一起做了。
- 這次實測請一併勾 P10。摘要「P10 直播時鐘」一節會列出：
  - 在最新期間 A 的範圍。超過 10 秒會列入異常，代表假設不成立。
  - currentTime 速度與 seekEnd 速度。
  - currentTime 不連續的次數。

**修正**：
1. 在最新（徽章「最新」）且播放中時，每秒取一個 A，最多 60 個，取中位數。每次回到最新都重新量：從倒轉回來，或在最新時跳轉。
2. 倒轉時的目標＝`A + currentTime − 同步微調`，時間碼換算用同一公式。**完全不用 `seekEnd`**。DVR 範圍的上限改取 `seekEnd` 與目前播放位置較大者，因為 `seekEnd` 會停住。
3. **進入頁面時就不在最新**（本頁沒量過 A）：
   - 不同步、清單不動、時間碼不可點。
   - 提示「請先點播放器的『直播』回到最新一次，藍框才能對齊」。
   - 不再沿用其他分頁或其他時間記下的基準：v44 的 `liveSync.baseline` 移除，因為 `currentTime` 的起點每次載入可能不同。
4. **同步微調的文字**：
   - 改為「同步微調：藍框提早 N 秒／藍框延後 N 秒」，下面加一行說明：「按 + 藍框往較新的訊息移動，按 − 往較舊移動」。
   - 按鈕方向也依這個說明：v44 的 + 是往較舊。
5. **v44 的校正值不沿用**：
   - 你調過的 −110 秒，是在錯誤的錨點上校正的。
   - 儲存改用新的 key `liveSyncV2`，所以第一次會顯示「0 秒（預設）」。
6. 連線狀態新增「錨點 N 樣本、範圍 X 秒」；「seekEnd 速度」保留作參考。

**為什麼這樣能解決 20.6 的現象**：
- v44 的目標是從 `seekEnd` 推回去的。`seekEnd` 停住時，倒轉量幾乎沒有反映到目標上，所以差距約等於倒轉量。
- 新做法只看 currentTime 的變化。倒轉 N 秒，目標就早 N 秒，與 `seekEnd` 無關。
- 測試模擬了實機數字（seekEnd 停在 currentTime + 3,486 秒、速度 0.00），倒轉 1、2、3 分鐘各播放 20 秒，藍框都落在對應的 N 秒前。
